# Deliverables catalogue

Each deliverable has a plugin skill (`skills/deliverable-<type>/`, named
`shipitright:deliverable-<type>`) that holds its template, the list of what is required, recommended
or optional, and its quality rules. This table gives the overview: who produces what, when, where.
Paths `team/…` and `skills/…` start from the plugin root, written `<plugin root>` (the agent file or
skill that points here gives the real path, see `team/glossary.md`); paths `docs/…` and `.team/…`
start from the project root.

Document deliverables, epics and stories included, are **static HTML pages** that rely on
`docs/_assets/doc.css` and `docs/_assets/doc.js`; the roadmap also loads `docs/_assets/plan.js`, which
computes its calendar. The team's internal working files (tickets, forum, questions) and the API
contract stay in Markdown or YAML. ADRs are HTML pages, one per decision; their register
`docs/adr/index.html` is generated by `team/scripts/adr-pages.mjs`. Questions also have a reading
page, `docs/questions.html`, generated by `team/scripts/questions-page.mjs`. The dashboard
(`docs/index.html`), the backlog page (`docs/20-specs/backlog.html`) and the analyses inventory
(`docs/10-analysis/index.html`) are generated by `team/scripts/dashboard-pages.mjs` from the project
files; `check-deliverable.mjs` runs its `--check`. The API contract has its own: the endpoint and
schema pages of the detailed design, the open points view and the Swagger UI view, generated by
`team/scripts/detailed-pages.mjs` (its `yaml` dependency is installed with the plugin).

## Requirement levels

In each template, each section carries a level:

- **required**: the deliverable does not pass its gate without it. `check-deliverable.mjs` blocks if
  it still contains a `.todo` placeholder.
- **recommended**: expected in the general case. Omitting it is justified in one line in the section
  ("not applicable: no external system"); it is not deleted silently.
- **optional**: useful when the project justifies it. Deleted without justification.

## Checking a deliverable

```sh
node <plugin root>/team/scripts/check-deliverable.mjs docs     # from the project root
```

On a `docs/` folder that contains the API contract, the script also runs
`detailed-pages.mjs --check`: a generated page not up to date or a broken reference gives a KO. It
also runs `adr-pages.mjs --check` and `dashboard-pages.mjs --check`: an ADR register or a dashboard,
backlog or analyses inventory page no longer up to date gives a KO. The API contract is also checked
with the Redocly lint, from the project root:
`npx @redocly/cli@2.58.2 lint docs/30-design/api/openapi.yaml` (criterion: no error). Run from
there, it does not read `.redocly.lint-ignore.yaml`: the warnings that file ignores reappear, and do
not count.

In the browser, a banner at the top of each page lists the required sections still to complete.
Adding `?levels` to the URL shows the level of each section.

## Rules common to all deliverables

- **Start from the template**, never from a blank page: `<plugin root>/skills/deliverable-<type>/template.html`,
  read with Read then written with Write at its place in the project (the deliverable's skill gives
  the path).
- **Do not touch `doc.css` or `doc.js`** from a deliverable. A component is missing: add it in
  `team/assets/` of the ShipItRight repository, then copy it into the projects.
- **Header filled in**: project, version, date, author (role; for an analysis, "AI" or the person's
  name), status (`draft`, `in review`, `validated`), sources. Some formats have their own statuses,
  detailed in their skill: analysis (workstream progress `in progress`, `done`, `partial`, in
  addition to the page status), campaign (`in progress`, `done`), sprint (`planned`, `in progress`,
  `closed`), acceptance report (`prepared`, `signed`, `refused`). The campaign and the acceptance
  report also carry their verdict in a `<meta name="verdict">` tag (glossary), read by the dashboard.
- **A hypothesis is visible**: `callout hypothesis` block; in the detailed design, hypothesis column
  of an open point. An open question too: badge
  `<a class="qmark" href="../questions.html#Q-xxx">Q-xxx</a>` at the place concerned, never a bare
  `[?]`. Every open question therefore has its file in `.team/questions/`; whoever creates or answers
  it regenerates the page: `node <plugin root>/team/scripts/questions-page.mjs .`.
- **No real data**: people, customers, amounts are fictitious.
- **Identifiers are stable and every reference is a link.** A deliverable cites the others by their
  identifiers; each citation points to the place where the element is defined, and that element
  carries an anchor equal to its identifier. A reference to a deliverable that does not exist yet is a
  link to its planned target. Prefixes, deliverable that defines each identifier and table of link
  targets: `team/glossary.md`. `check-deliverable.mjs` reports broken links (anchor missing from an
  existing deliverable: KO; file not produced yet: warning) and prefixes missing from the glossary
  (warning).
- **The deliverable is reviewed before its gate** by a fresh Reviewer, who checks completeness and
  consistency with the other deliverables.
