# Framework glossary

Single source of the team's identifiers, abbreviations and vocabulary. Other files (`team-rules`,
`team/deliverables.md`, skills, conventions) point here and do not copy these lists. A new prefix, a
new abbreviation or a term with a precise meaning is added here first.

This glossary describes the framework. A project's business glossary (domain terms) lives in its
framing, section Glossary.

**Paths and names.** In the framework documents read with Read (`PROCESS.md`, `team/…`), a path
`team/…`, `skills/…` or `agents/…` starts at the plugin root, written `<plugin root>`: an agent file or
a skill gives its real path (the plugin root variable is substituted only in agent files and skills,
not in a document read with Read). A script is therefore run as
`node <plugin root>/team/scripts/<script>.mjs .`, from the project root. A path `.team/…`, `docs/…` or
`prototype/…` starts at the project root. A skill or an agent of the plugin is invoked by its prefixed
name, `shipitright:<name>`; in the Source columns of this glossary, `deliverable-<type>` means the skill
`shipitright:deliverable-<type>`.

## 1. Identifiers

An identifier is stable: it does not change when the deliverable evolves, and it is never reassigned.
A deliverable cites the others by these identifiers, and each citation is a link to the place where the
element is defined. That element carries an anchor equal to its identifier (`<tr id="BR-04">`,
`<div class="card" id="PER-01">`), unless it has its own page.

Targets are written from a first-level folder of `docs/` (`docs/10-analysis/`, `docs/20-specs/`…). From
a subfolder (`docs/20-specs/stories/`), add one `../` per subfolder level. A reference to a deliverable
that does not exist yet is a link to its planned target; `check-deliverable.mjs` reports it as a warning
(target not produced yet).

For `EP-xx`, `EN-xx` and `PROC-xx`, while the detailed page does not exist, the link falls back to
`../30-design/macro.html#<ID>`.

The `#Sn` anchor of a scenario is created by `doc.js` when the story loads. In a text (ticket, test
name, campaign, `BUG-xxx`), write `US-006/S4`.

A functional rule (`Rn`, `<tr id="Rn">`) and an example data set (`Dn`, `<tr id="Dn">`) of a story are
written without prefix inside their story. Outside their story, write `US-006/R2` and `US-006/D2`,
linked to `…/US-006-<slug>.html#R2` or `#D2`, like scenarios.

**Release and sprint in a text.** A release keeps its sigil (`R2`, `R3`, `Rn`, see the abbreviations),
but a sentence always writes "release R2", never `R2` alone; labels and attributes
(`data-release="R2"`, `<span class="tag">R2</span>`) keep the sigil alone. A sprint is always written
"sprint N" ("sprint 2"), never `S2` or `SN`: `Sn` is reserved for the scenario of a story.
The retro identifiers, `S2-P1`, `S2-A1`, `S2-E1`, carry the sprint number as prefix and are never
written without their suffix; they do not replace "sprint 2" in a sentence. Prefixed with the number
of the sprint page that defines them, they are unique in the project and anchor their row
(`<tr id="S2-P1">`); elsewhere, `S1-A2` is a link to `sprint-1.html#S1-A2`.
`check-deliverable.mjs` checks this, as a warning: it reports an isolated `Rn`, `Dn` or `Sn`, except a
release preceded by "release" or "releases", the continuation of a qualified list ("`US-006/S1` to
`S7`"), a label (class `tag` or `sm-release`, attribute `data-release` or `data-rel`, element whose
whole text is the sigil), a quotation, and a `#Sn` link inside its own story. A short label that fits
none of these cases (the "Story R2" legend of the story map) carries `class="abbr"` or `data-abbr`:
that is the explicit exception.

**References without prefix**, for the detailed design and the API contract:

| Reference | Means | Link target from `docs/<folder>/` |
|---|---|---|
| `<Schema>` | schema exchanged by an endpoint | `../30-design/detailed/schemas/<Schema>.html` |
| `<Type>` | type shared between schemas | `../30-design/detailed/schemas/index.html#<Type>` |
| `v<version>` | version of the API contract | `../30-design/detailed/schemas/index.html#v<version>` |
| `<CODE>` | API error code | `../30-design/detailed/cross-cutting/errors.html#<CODE>` |

**What is not an identifier.** These names have the shape of an identifier but designate a technical
standard. `check-deliverable.mjs` accepts them without counting them as prefixes: `SHA-256`, `UTF-8`,
`ISO-8601`.

`check-deliverable.mjs` reads this part: in the text of a deliverable, outside code and attributes, an
identifier made of two to five capital letters, a hyphen and digits, whose prefix is not listed here,
gives a warning. A prefix is declared between backticks in the first column.

## 4. Story statuses

The backlog page shows the status of a story on a single scale, in the order of the flow. It is read
from the `<meta name="status">` tag of the story, except "To write" (no page yet) and the sprint number
(read from the sprint page).

| Displayed status | Value of the `status` meta | Meaning |
|---|---|---|
| To write | (no page) | the story is in the story map, its page does not exist yet |
| Written | `draft` | its page exists, its Definition of Ready is not checked yet |
| Ready | `ready` | its Definition of Ready is checked (an XL story never is) |
| Validated | `validated` | validated by the human at G1 (`validated_by`: the person's name); written after G1, validated by the PO (`validated_by` `ai`) and shown at the next G3, or raised earlier to the human (`validated_by`: the person's name) |
| In sprint N | `in-sprint` | committed in sprint N, according to its sprint page |
| Delivered | `done` | accepted in a signed acceptance report, with or without reservations; the report is authoritative |
| Abandoned | `abandoned` | struck through at the end of its epic, out of the counts |
