Sécurité et droits : qui appelle quoi

Session, rôles, contrôles sur les données. Le backend contrôle, le front ne fait que masquer. Les principes sont dans la conception macro ; ici, leur application endpoint par endpoint.

Version v0.3 Date 08.10.2026 Auteur Architecte (exemple de format) Statut en revue

Session et contrôle d'accès

À quoi sert
Dire comment une requête est authentifiée, puis autorisée.
Contenu
  • Le mécanisme de session.
  • Le contrôle commun avant chaque route.
  • La déclaration des rôles par route.
  • La place des contrôles sur les données.
Pourquoi ce formalisme
Les principes de la conception macro appliqués au code, en liste courte, chacun avec l'invariant qui le rend vérifiable.
  • Session serveur, cookie opaque rs_session HttpOnly, SameSite=Strict, Secure hors local (ADR-0003, EN-02). SameSite=Strict et la même origine dispensent d'un jeton anti-falsification.
  • Un contrôle commun, avant chaque route, lit la session et repousse son expiration ; sans session valide, UNAUTHENTICATED. Seules EP-01 et EP-03 sont publiques.
  • Chaque route déclare les rôles admis ; une route sans déclaration fait échouer le démarrage (INV-08). Rôle insuffisant : INTERDIT.
  • Les contrôles sur les données (titulaire, motif) vivent dans le domaine, pas dans la route (INV-04).

Matrice des droits

À quoi sert
Savoir qui peut appeler quoi.
Contenu
En lignes les endpoints, en colonnes les rôles (oui ou non), puis les contrôles sur les données au-delà du rôle.
Pourquoi ce formalisme
La matrice d'accès rôles × opérations, forme standard d'un contrôle d'accès par rôle (RBAC).
Lire
Un endpoint public est aussi ouvert aux rôles.

Données et protections

À quoi sert
Montrer ce qui protège les données.
Contenu
  • Les données personnelles et qui les voit.
  • Les mots de passe.
  • Les jetons.
  • L'injection.
  • Les journaux.
Pourquoi ce formalisme
Une ligne par sujet, avec l'invariant ou l'entité qui la porte : la revue de sécurité la suit telle quelle.
  • Données personnelles : nom et email des employés, rien d'autre, tout est fictif. Le nom du titulaire est visible de tous (EP-06) ; l'email et l'identifiant d'un autre employé ne sortent jamais (INV-67).
  • Mots de passe : empreinte scrypt seulement (EN-01), comparaison en temps constant, jamais journalisés ; limite de 5 tentatives par minute et par adresse (EP-01).
  • Jetons : 32 octets aléatoires, seule leur empreinte SHA-256 est en base (EN-02).
  • Injection : requêtes préparées seulement (INV-06) ; schémas JSON stricts sur chaque route, champ inconnu refusé (INV-63 pour le titulaire).
  • Journaux : une ligne JSON par requête, identifiants techniques seulement, ni nom ni email (INV-52).
