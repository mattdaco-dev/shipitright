Gestion des erreurs : codes, statuts, écrans

Chaque erreur de l'API porte un code métier stable que le front traduit en message. Le catalogue ci-dessous est tiré du contrat d'API : il dit pour chaque code le statut HTTP, le cas, ce que voit l'utilisateur et les endpoints qui le renvoient.

Version v0.3 Date 08.10.2026 Auteur Architecte (exemple de format) Statut en revue

Principes

À quoi sert
Dire comment une erreur circule de l'API à l'écran.
Contenu
Le format des erreurs, le choix du statut HTTP, la traduction par le front, le traitement d'un code inconnu.
Pourquoi ce formalisme
Une liste courte, chaque principe avec l'invariant qui le rend vérifiable ; le détail code par code est dans le catalogue.
  • Format application/problem+json (RFC 9457), schéma Probleme (ADR-0004). Le champ code prend une valeur de CodeErreur.
  • Conflit d'état en 409, règle de saisie en 422, requête hors schéma en 400, rôle insuffisant en 403.
  • Le front traduit le code, jamais title ni detail (INV-64). Les libellés viennent du catalogue unique (INV-65).
  • Un code que le front ne connaît pas (valeur ajoutée par une release suivante) s'affiche comme l'erreur technique de l'écran, sans planter (INV-59). Les codes annoncés portent leur release dans le catalogue.
  • Un code qui met en cause un objet (colonne Entité) n'est renvoyé que par un endpoint ou un traitement qui déclare cette entité ; le générateur le vérifie. La traduction écran par écran est dans la vue écrans.
  • Aucune réponse ne porte de détail technique : ni pile, ni SQL, ni nom de table (INV-09). Une erreur imprévue annule la transaction et répond INTERNAL_ERROR.
  • Une saisie bornée par l'écran (sélecteurs, cases à cocher) ne devrait jamais produire de 400 ou de 422 : quand elle en produit, c'est un défaut, affiché comme l'erreur technique de l'écran.
