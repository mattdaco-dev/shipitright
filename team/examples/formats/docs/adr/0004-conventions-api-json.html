ADR-0004 : API en JSON simple, erreurs problem+json

Statut accepté Date 06.10.2026 Remplace aucun Remplacé par aucun Répond à aucune question Écart au socle non

Contenu

Non. Le socle node-sqlite-angular impose OpenAPI 3 mais pas de format d'échange ; le gabarit de la team retient par défaut JSON simple et problem+json.

Contexte

À quoi sert
Dire ce qui force un choix, pour qu'un lecteur le comprenne sans autre source dans trois mois.
Contenu
Le problème, les contraintes du cadrage, du socle et des règles de gestion, et le volet de la question à laquelle l'ADR répond.
Pourquoi ce formalisme
Quelques phrases de prose, comme dans le format ADR de Michael Nygard : le contexte se raconte, il ne se tabule pas.

openapi.yaml est le contrat d'API entre back et front. Il faut fixer le format des corps, des erreurs et des listes avant de le rédiger. Les listes du produit sont courtes (une dizaine de salles, une journée de réservations, les réservations à venir d'un employé).

Décision

À quoi sert
Dire ce qui est décidé, applicable tel quel par un dev.
Contenu
Une affirmation par choix, à l'affirmatif, sans condition ni alternative.
Pourquoi ce formalisme
Une liste : chaque choix se cite seul en revue ou dans un invariant ; l'affirmatif ne laisse aucune lecture hésiter.
  • Corps en application/json, ressources à plat, identifiants entiers, dates AAAA-MM-JJ, heures HH:MM dans l'API (minutes seulement en base).
  • Erreurs en application/problem+json (RFC 9457), avec un champ code métier stable (CRENEAU_PRIS, CRENEAU_HORS_REGLES, SERIE_TROP_LONGUE, NOM_SALLE_PRIS…) que le front traduit en message MSG-xx. Conflits en 409, règles de saisie en 422.
  • Pas de pagination au MVP : les listes sont bornées par leurs filtres (une journée, les réservations à venir). Filtres en paramètres simples (?jour=2026-10-06&salle=3).
  • Toutes les routes sous /api.

Raison

À quoi sert
Dire pourquoi cette option, et pourquoi pas les autres.
Contenu
Les arguments de la décision, puis une ligne par option écartée avec la raison de l'écarter.
Pourquoi ce formalisme
Le tableau des options considérées du format MADR : une option écartée et sa raison restent visibles, et le débat ne se rouvre pas sans fait nouveau.
  • JSON simple : le plus direct pour Fastify et Angular, schémas JSON réutilisés tels quels dans OpenAPI.
  • problem+json : format standard, et le code métier découple le texte affiché (au mot près, côté front) de l'erreur serveur.

Conséquences

À quoi sert
Dire ce que la décision implique, en bien et en mal, et ce qu'elle oblige à faire.
Contenu
  • Positif : ce qu'elle apporte.
  • Négatif : ce qu'elle coûte, la dette acceptée.
  • Suites : les actions à prévoir, avec le livrable ou le rôle qui les porte.
Pourquoi ce formalisme
Trois termes fixes : un ADR sans négatif cache un coût, un ADR sans suite n'a rien changé.
Positif
contrat court et lisible, mock front facile ; aligné sur les conventions par défaut du gabarit : le squelette du contrat d'API sert tel quel.
Négatif
pas de pagination au MVP : une liste qui grossit demandera un ajout annoncé au contrat d'API (INV-58).
Suites
Architecte : reporter ces conventions dans le socle complété, et ajouter une pagination par curseur au sprint planning où une liste grossit (historique, statistiques de la release R3).
