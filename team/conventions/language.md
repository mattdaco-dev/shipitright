# Language of a project

A ShipItRight project is written in **one language**, chosen at `project-init`: all the visible text
of the deliverables, generated pages, prototypes and questions to the human. The language is open:
`fr`, `en`, `de`, `pt-BR`, any BCP 47 code. The plugin provides the `fr` and `en` labels; for another
language, the PO translates the labels at `project-init` (section 5).

What is never translated, whatever the language: code, identifiers (`US-012`, `BR-03`, `S2-A1`), file
names, commit messages (English), attributes (`id`, `class`, `data-*`, `<meta name>` and their coded
values), content of `<script type="application/json">`.

## 1. Where the language lives

`.team/project.json`, written by `init-project.sh --lang <code>`:

```json
{ "language": "de" }
```

Without this file, the language is `en`.

Each HTML deliverable carries the project language on its root: `<html lang="de">`. Templates are
written with `lang="en"`: the agent that copies a template replaces the value.

## 2. Templates: the structure, not the text

A template gives the structure of a deliverable. The agent that fills it writes **all the visible text
in the project language**, section headings and header labels included (`<b>Status</b>` becomes
`<b>Statut</b>` in French). It translates neither attributes nor coded values: those are what the
scripts read.

The section headings of the templates carry a fixed `id` (`<h2 id="coverage-matrix">`): translate the
heading, never the `id`, and links from one deliverable to another stay valid. A section added and
cited elsewhere also gets an explicit `id`.

## 3. What scripts read: never visible text

A script or `check-deliverable` never finds a field, a section or a value by its visible label. It
reads:

| What | Where | Example |
|---|---|---|
| Header field | `<meta name="<code>" content="<value>">` in `<head>` | `<meta name="date" content="2026-10-02">` |
| Section | attribute `data-section="<code>"` on the `<section>` | `<section class="section" data-section="results">` |
| Table column | attribute `data-col="<code>"` on the `<th>` | `<th data-col="nature">Nature</th>` |
| Value of an element | attribute `data-value="<code>"` (`<td>`, `<dt>`, `<p>`…) | `<td data-value="trial">Versuch für einen Sprint</td>` |
| Date | ISO `YYYY-MM-DD` in the meta or `datetime` | `<time datetime="2026-10-02">2. Oktober 2026</time>` |

- Codes (`data-section`, `data-col`, meta names, coded values) are English: `data-section` and
  `data-col` in kebab-case, meta names as the formats define them (`acceptance_date`, `start-date`).
- **Coded values** are English codes: `status` (`draft`, `validated`, `done`…), `verdict`
  (`favorable`, `unfavorable`…), `data-level` (`required`…). They are never displayed as is: the page
  displays their label in the project language.
- No script falls back on reading visible text when a meta or an attribute is missing: the missing
  code is reported.

Files without attributes (Markdown, YAML): the structure is read from a fixed form, never from a word.

- YAML schema of the API: first line `# domain: <domain label>`.
- Question (`.team/questions/`): `##` sections in a fixed order, question, context, hypothesis,
  answer, whatever their headings (format: `team/conventions/forum.md`).
- Hand-written deliverable: `<meta name="status">` (`draft`, `in-review`, `validated`) and
  `<meta name="date">` (ISO), kept up to date with its header; the templates already carry them. The
  dashboard reads only those.

## 4. Journal: the decision of a gate

A gate line carries its decision as a code, right after the gate, then the name of the person who
decided, then free text in the project language:

```
2026-10-02 14:10 · G1 · validated · Claire Martin · functional design validated, P2 comments addressed
2026-10-09 11:00 · G2 · changes-requested · Claire Martin · three comments on the booking API
2026-10-20 17:30 · G3 · accepted-with-reservations · Paul Durand · sprint 1 (RES-01, RES-02)
```

The name is the real name of the person (decider, `team/glossary.md`), never the word "human":
`dashboard-pages.mjs` rejects a gate line without it.

Codes: `validated`, `changes-requested` for G0 to G2; for G3, the code of the acceptance report
`verdict` (`accepted`, `accepted-with-reservations`, `rejected`). The other lines (`dispatch`,
`report`, `incident`, `resume`…) keep their type as an English code, and their text in the project
language.

## 5. Labels of generated pages and assets

Fixed labels (pages generated by the scripts, `doc.js`, `plan.js`) come from dictionaries:

```
team/i18n/<language>/<namespace>.json   provided by the plugin, languages fr and en
.team/labels.json                       specific to the project: { "<namespace>": { "<key>": "…" } }
```

- A dictionary is a flat object `{ "<key>": "<label>" }`; the full key is `<namespace>.<key>`.
  Namespaces: `common`, `init`, `dashboard`, `detailed`, `adr`, `questions`, `doc`, `plan`, `gherkin`.
- Parameters in braces: `"{n} stories out of {total}"`. A label that depends on a number is an object
  of CLDR plural forms, chosen by `Intl.PluralRules` on the parameter `n`:
  `{ "one": "{n} story", "other": "{n} stories" }`.
- No compound agreement at run time (unit + agreed participle): each sentence is a whole key.
- Resolution of a key: `.team/labels.json`, then the exact language (`pt-BR`), then its base language
  (`pt`), then `en`. A key missing everywhere is displayed as is and `check-deliverable` reports it.
- Displayed dates: short format given by the label `common.date.short` (`dd.mm.yyyy` in `fr`,
  overridable by the project), else `Intl.DateTimeFormat` in the project language; numbers:
  `Intl.NumberFormat`.

**Language without a provided dictionary**: at `project-init`, the PO translates the files
`team/i18n/en/*.json` into the project language and writes `.team/labels.json`, keeping keys and
parameters. For the `gherkin` namespace, the PO uses the official Gherkin keywords of that language.

**Browser side**: `node <plugin root>/team/scripts/i18n-assets.mjs .` writes `docs/_assets/i18n.js`
(`window.SIR_I18N = { lang, labels }`, namespaces `common`, `doc`, `plan`, `gherkin` already
resolved). `init-project.sh` runs it, `dashboard-pages.mjs` runs it again at each regeneration.
`doc.js` and `plan.js` load it from their own folder before rendering anything. The prototype does
not depend on it: the `proto-bar` bar has its own `fr` and `en` labels and takes `labels` for another
language.

## 6. Shared code

`team/scripts/lib/i18n.mjs`: `projectLang(dir)`, `loadLabels(dir, namespaces)`, `makeT(lang, labels)`,
`formatDate(iso, lang, style)`, `writeClientI18n(dir)`. The scripts import it, none re-implements its
own resolution.
