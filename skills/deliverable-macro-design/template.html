Principles of the model
  1. Screens present features. A feature can serve several screens.
  2. A feature relies on one or several endpoints or external services.
  3. Endpoints and processes act on one or several entities.
  4. An entity and an endpoint appear only once: converging arrows show the reuse.
  5. An endpoint is exposed and callable, a process is not: two distinct columns.
  6. A call to another domain starts from an endpoint or a process, never from a feature.
  7. A topic never reaches an entity: it pushes to a process, which writes into the entity. It lives in the domain that publishes it.
  8. The HTTP verb is in the endpoint block, never on the arrow.
  9. An external system is a system, not a piece of data: the arrow says what is fetched there.
  10. External means external to the organization. An internal team is a neighbouring domain.
  11. Labels are readable text in the project language, endpoint paths stay literal.

Technical chain diagram

Purpose
Show what must be built and where, from screen to entity, for the whole project.
Content
The counters per block type, then a single diagram: screens and features in the application; endpoints, processes and entities in the domain; each block with its identifier and its release.
Why this formalism
The screen-endpoint-entity chain, read from left to right: an arrow that crosses the boundary is a contract between front and back. Each block appears only once, which shows the reuse.
Reading
  • The scope filter shows one release: its blocks as TODO and, in context, those of earlier releases it calls (DONE) or adapts (TO UPDATE); the counters follow.
  • Hovering a block lights up its chain; clicking it opens the chain alone in a centred view.
  • The identifier of a block opens its page of the detailed design; the { } icon of an endpoint shows its schemas.
Source
The arrows: data-links on the start block. The filter: data-release and data-adapted of each block.

Architecture decisions

Purpose

Content
