Compliance contract: the invariants of the code

What the code respects, whatever the ticket. The dev self-reviews against it before handing in, the Reviewer checks each invariant and cites it by its identifier. An invariant not respected is blocking, unless there is an accepted deviation with its ADR.

Stack foundation invariants

Purpose
Say which invariants of the stack apply to the project.
Content
The foundation declared, the invariants taken by reference, those that do not apply with their reason, and, as long as the foundation is "to be completed", the provisional invariants it will have.
Why this formalism
The invariants of a foundation serve several projects and live in its compliance.md: taking them by reference avoids two versions of the same invariant. A provisional invariant already carries the identifier it will have in the foundation: neither the code nor the reviews will have to change.
Reading
An invariant taken by reference has no row here: a page that cites it links to this section (compliance.html#stack-foundation), the generator does it on its own.
Foundation declared
name and version of the foundation of .team/foundation.md; invariants INV-01 to INV-49 of .team/foundations/stacks/<name>/compliance.md (or of the source it points to), taken by reference, as is
Not applicable
"none", or each invariant set aside with its reason, taken over in the accepted deviations

Provisional invariants of the foundation

Only if the foundation is "to be completed" (no compliance.md, or a part of the stack without an invariant); otherwise remove this subtitle and the table. They apply to every ticket of the part concerned until the foundation is completed, where they will be carried then removed from here; the human validates them with the foundation at G2 (open point of the code organization, high impact). They translate the ADRs of the macro and the code organization.
