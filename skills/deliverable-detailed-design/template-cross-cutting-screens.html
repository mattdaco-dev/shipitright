Screens: what each screen calls and translates

The view of the frontend dev: for each screen of the macro design, the endpoints it calls, the error codes it must translate and the messages it displays, then its address, what comes to it from another screen and the accessible roles and names the e2e tests target. The behaviour of each code is in the error handling.

Screen map

Purpose
See all the screens of the product, how one goes from one to another, and go to their definition.
Content
One card per screen of the macro design, grouped by journey: preview and name from the UX/UI spec, link to its definition and to its "By screen" row. The arrows carry the action that leads from one screen to another.
Why this formalism
A wireflow, the counterpart of the site map for the front, drawn with the same engine as the one of the UX/UI spec.
Reading
  • A screen present in two journeys is drawn once.
  • A dialog counts for its screen.
  • Results and going back are not drawn.
  • A screen without a journey is at the end, without an arrow.
Source
The screen inventory and the wireflow of the UX/UI spec, and the macro design. The wireflow stays the only source of the transitions.

By screen

Purpose
Serve as the entry point of the frontend dev, screen by screen.
Content
For each screen of the macro design: the endpoints it calls, the error codes it translates, the messages it displays, and the link to its "Address, landing and structure" row.
Why this formalism
A table, one row per screen: the dev reads at once everything their screen touches.
Reading
A screen of a later release, not yet in the UX/UI spec, stays without a link.
Source
The screen, feature, endpoint chain of the macro, the x-codes of openapi.yaml, the error catalogue and the sequences.

Address, landing and structure

Purpose
Say, before the dev, how one lands on each screen and what the e2e tests target there, so that neither the frontend dev nor QA has to guess.
Content
One row per screen of the macro design: address and parameters (path, path and query parameters), what comes from another screen (origin screen, message carried and mechanism: address parameter, navigation state), accessible roles and names of the elements the e2e tests target.
Why this formalism
The page objects of the e2e tests and the screens are built in parallel: they agree on this table, written once, rather than on the assumptions of each ticket.
Reading
An accessible name is the exact label of the UX/UI spec. A screen of a later release keeps its row, with what is already known.
Source
Written by hand by the Architect, reviewed by the UX and QA, from the UX/UI spec (content, actions, wireflow) and the code organization. The generator flags a screen of the macro without a row.
