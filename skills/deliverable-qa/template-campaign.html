Scope

Purpose
Say what the campaign tested, with which tests and where, so that a result is never read out of its context.
Content
The stories of the sprint, the merged e2e tickets the tests come from, the environment, the dates, the state of the entry criteria.
Why this format
A definition list, one topic per term. The e2e tickets are cited because the suite played is the one they merged: a test absent from a merged ticket does not exist for the campaign.
Read
Commits are in the runs, not here: there is one per redeployment. The entry criteria are those of the strategy: only their state is written here.

Runs

Purpose
Know on which version each result was obtained, and prove that the results of the verdict come from the last commit.
Content
One row per event on "Demo and acceptance", in order: start, suite run, bug opened, redeployment after the merge of a fix, replay, reset.
Why this format
A dated log, one row per event, like a test log (ISO/IEC/IEEE 29119-3): the commit of each row ties a result to the code that produced it. The last commit of sprint/N played, replays included, is the accepted commit, which the acceptance report takes over.
Read
A suite run is done twice at the same commit; the second without the limitation project (test data). The double run of the exit criterion is done at the accepted commit: a fix merged at the end of the campaign is therefore replayed twice there. The results by scenario are those of these two runs. A BUG-xxx test of an unfixed bug stays on its branch: it is not in sprint/N and does not run at the accepted commit. The reset is the last row: after it, no test runs before pre-acceptance.

Results by scenario

Purpose
Show, scenario by scenario, that each acceptance criterion of the sprint has a green test, or why it does not.
Content
One table per story, one row per scenario US-xxx/Sn: the test that proves it, its result in the two runs of the accepted commit, the bug or cause that explains a result that is not green.
Why this format
The strategy matrix says what is planned; this table says what happened, with the same identifier. Four results: green, red (a bug is open), blocked (the cause is written), not run (the reason is written). A result with no test, bug or cause does not count.
Read
Test "e2e": the one that carries the scenario identifier, under the naming rule of the matrix. A scenario without e2e in the matrix is proven by the test of the complementary level it names; it has no second run, it is not an e2e. A bug fixed during the campaign stays cited, with the commit of its fix. A blocked or not run scenario has no green test, even with its cause written: it misses the first exit criterion and makes the verdict unfavorable.

Bugs

Purpose
Follow each bug opened during the campaign up to its effect on the verdict.
Content
One row per bug: scenario affected, severity, fix branch, BUG-xxx test red then green, status in the board, effect on the verdict.
Why this format
Steps, expected, actual and proof are in the bug file, in the board: the campaign does not copy them, it traces the circuit of the strategy. The test red then green, with its commits, proves the fix better than a status.
Read
Status: the board's, kept by the PO. "Admitted": open and without a blocking effect on the verdict, because minor, or major accepted in writing by the PO in the verdict; the scenario it turns red is cited there. An admitted minor stays at status backlog; at acceptance, the PO carries it over as a reservation RES-xx of the acceptance report. No bug: say so.

Non-regression

Purpose
Prove that the sprint did not break what previous sprints delivered.
Content
One row per story of the previous sprints, then the non-functional tests of the previous sprints, the tests of closed bugs and the API contract version: number of tests, result in the two runs of the accepted commit, regression found.
Why this format
The replayed suite and the entry rule are in the strategy; here, only their result, per story, so that a regression points at once to what it affects. The same exit criterion as for the sprint scenarios: green, except a test an admitted bug turns red, cited here.
Read
Required: an exit criterion depends on it. A flaky test is written in "Regression or instability", with what is done about it. The numbers of this section plus the e2e added in the sprint make the e2e total of the test count. First sprint: "not applicable, no previous sprint".

Non-functional tests

Purpose
Show that the non-functional checks due this sprint are within their thresholds.
Content
One row per check played: the environment of the measurement, the number of measurements, the measured value against the threshold, the status.
Why this format
The check, its tool, its threshold and its frequency are in the non-functional tests of the strategy; here, what was measured, where, and how many times. The threshold is recalled in figures only, next to the measurement, so that the row is judged without going back and forth.
Read
A measurement only counts in the environment its target names (environments). Required: an exit criterion depends on it. A manual check has its proof versioned in docs/40-qa/evidence/sprint-N/, linked from its row. A strategy check not due this sprint, by its frequency, has no row: the last row names them.

Test count

Purpose
Record, sprint after sprint, the number of tests at each level, so that the shape of the pyramid can be checked.
Content
One row per level of the pyramid: the runner, the number of tests it reports at the accepted commit, what the sprint added.
Why this format
A number reported by a runner can be checked; "enough tests" cannot. Orders of magnitude are in the strategy, this page does not copy them: the gap is discussed at the retro, over the series of counts.
Read
Level names are those of the pyramid, word for word. The number is the runner's, not a hand count. e2e total: the tests of the non-regression plus those added in the sprint; a BUG-xxx test left on its branch is not counted.

QA verdict

Purpose
Give the PO a verdict that follows from the campaign, and tell them how to prepare the acceptance.
Content
The counters of the accepted commit, the state of each exit criterion of the strategy, the verdict, the admitted bugs and the scenarios they turn red, the PO's written acceptances, the recommendation for the acceptance.
Why this format
The exit criteria of the strategy, each met or not met, with the link to the section that proves it: the verdict follows, it is not negotiated. Three verdicts: favorable without reservations (all criteria met, no open bug), favorable with reservations (only minors open, or a major accepted in writing by the PO), unfavorable (an open blocking bug, an open major not accepted, or another criterion missed).
Read
A blocked or not run scenario has no green test: the first criterion is not met and the verdict is unfavorable. Only a major can be accepted, and only in writing, by the PO, in this section, with the date. The PO only prepares the acceptance on a favorable verdict, with or without reservations (G3).
