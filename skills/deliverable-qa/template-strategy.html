Purpose
That a test always starts from a known state, with fictional data, without depending on another test or another story.
Content
The base data set, each test's own data, the story data sets, the dates, the sessions, the reset, the edge cases; then the accounts per role and their passwords.
Why this format
A definition list, one topic per term; the accounts as a table, one row per role.
Read
The data sets of a story (D1, D2…, anchored #Dn) are in its "Example data" section; outside the story, they are cited US-xxx/Dn as a link: the test reuses them, this page does not copy them.

Data of a test
test seed (fixture) that prepares the situation of each test without going through the endpoints of a story, so as not to depend on delivered stories; unique name per run (scenario and run identifier) so that no test or run shares data; tests independent of their order

Limitation test

Campaign entry and exit criteria

Purpose
Make the verdict of a campaign mechanical: it follows from these criteria, it is not negotiated.
Content
The conditions to start a campaign, then those of a favorable verdict.
Why this format
Entry and exit criteria of a test plan (ISO/IEC/IEEE 29119-3), as lists: each criterion is true or false.
Read
Favorable without reservations: all exit criteria met, no open bug. Favorable with reservations: the other criteria met, and only minor bugs or a major accepted in writing by the PO remain open, acceptance noted in the campaign. Unfavorable: an open blocking bug, an open major not accepted, or another exit criterion missed.

Entry

  • all tickets of the sprint are reviewed without a blocker and merged into sprint/N, e2e tickets included: the campaign runs at the commit that contains them;
  • build green, devs' tests green on sprint/N;
  • the QA has started the assembled application on the acceptance environment, at the commit noted in the campaign, and it answers;
  • project-specific criterion

Exit (favorable verdict, with or without reservations)

  • each scenario of the sprint stories has a green test (an e2e that carries its identifier, or, if the matrix marks it without e2e, the test of the complementary level), except those an open bug admitted at the verdict turns red (minor, or major accepted in writing by the PO), cited in the campaign;
  • each e2e replayed twice, same result; the second run runs without the limitation project;
  • no open blocking bug; no open major without the PO's written acceptance;
  • non-regression green, except the tests an open bug admitted at the verdict turns red (minor, or major accepted in writing by the PO), cited in the campaign;
  • non-functional checks of the sprint within their thresholds, if any

Coverage matrix

Purpose
Prove that no scenario is forgotten, and find the test of a scenario with one search.
Content
One row per Gherkin scenario: how the e2e plays it when not through the interface alone, and the lower-level test that proves the same rule.
Why this format
The requirement to test traceability matrix (RTM), with a shared identifier: US-xxx/Sn, the team glossary notation for scenario n of a story (anchor #Sn of the story), in the test name and in the campaign.
Read
Complete at G2: all scenarios of the stories validated at G1. A story added or changed after G2 updates the matrix at the sprint planning that takes it. Empty e2e means: the interface, by default. Only exceptions are written: API, network interception, two accounts, special input. without e2e: the reason is written, and the test of the complementary level is the one the exit criterion requires. The progress of a test and its result (passed, failed, blocked) are in the campaign, not here.

Bug management

Purpose
That a bug can be reproduced without the QA and that its severity does not depend on mood.
Content
The severity grid and its effect on the verdict, the content of a bug, its circuit.
Why this format
A three-level severity grid, each defined by its effect on the user; the circuit as an ordered list, aligned on the board statuses (team/conventions/ticket.md).

File

Content
steps from the base data set, expected, actual, commit of sprint/N, proof (screenshot, console, request and response), scenario US-xxx/Sn
Test
every bug gets a test that reproduces it, named BUG-xxx; it also carries US-xxx/Sn if it affects a scenario. When opening it, the QA creates the branch bug-xxx-<slug> from sprint/N in their worktree, commits the red test there, then removes their worktree; the dev reopens the same branch, without recreating it (team/conventions/git.md)
  1. The QA opens the bug and commits its red test on its branch bug-xxx-<slug>; the PO prioritizes it and assigns it to a dev in the sprint.
  2. The dev reopens the same branch and fixes it, until the test is green; a fresh Reviewer reviews it like a ticket (3 rounds at most), then the PO merges it into sprint/N.
  3. After the merge, the PO moves it to test; the QA replays its test and the linked scenario on the acceptance environment.
  4. Green: the PO closes it and the test joins the non-regression. Red: back to the dev, with the new proof.

Non-regression

Purpose
That a sprint does not break what a previous sprint delivered.
Content
The replayed suite, the entry rule of a test, the handling of a flaky test, the effect of a new API contract version.
Why this format
A definition list, one rule per term: the campaign applies them without rephrasing them.
Replayed suite
by default: the whole e2e suite of the previous sprints, target duration
Entry into the suite
a scenario test after its first favorable campaign; a bug test when the bug is closed
Flaky test
replayed twice by hand (retries: 0); if it stays flaky, noted in the campaign and fixed in the sprint, never silently disabled
API contract
by default: a new contract version that touches an operation already tested replays the stories that call it, even outside the sprint
