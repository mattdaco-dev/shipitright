Gestion des erreurs : codes, statuts, écrans

Chaque erreur de l'API porte un code métier stable que le front traduit en message. Le catalogue ci-dessous est tiré du contrat d'API : il dit pour chaque code le statut HTTP, le cas, ce que voit l'utilisateur et les endpoints qui le renvoient.

Principes

À quoi sert
Dire comment une erreur circule de l'API à l'écran.
Contenu
Le format des erreurs, le choix du statut HTTP, la traduction par le front, le traitement d'un code inconnu.
Pourquoi ce formalisme
Une liste courte, chaque principe avec l'invariant qui le rend vérifiable ; le détail code par code est dans le catalogue.
  • Format application/problem+json (RFC 9457), schéma Probleme. Le champ code prend une valeur de CodeErreur.
  • Requête hors schéma en 400, session absente en 401, rôle insuffisant en 403, ressource inconnue en 404, conflit d'état en 409, règle de saisie en 422.
  • Le front traduit le code, jamais title ni detail, depuis un catalogue unique de libellés.
  • Un code que le front ne connaît pas (valeur ajoutée par une release suivante) s'affiche comme l'erreur technique de l'écran, sans planter (CF-59). Les codes annoncés portent leur release dans le catalogue.
  • Un code qui met en cause un objet (colonne Entité) n'est renvoyé que par un endpoint ou un traitement qui déclare cette entité ; le générateur le vérifie. La traduction écran par écran est dans la vue écrans.
  • Aucune réponse ne porte de détail technique (pile, requête, nom de table). Une erreur imprévue annule la transaction et répond ERREUR_INTERNE.
  • règles propres au projet, ou retirer cette ligne

Catalogue des codes

À quoi sert
Tout savoir d'un code d'erreur métier.
Contenu
Une ligne par valeur de CodeErreur : statut HTTP, cas, ce que voit l'utilisateur (écran et message), entité mise en cause, endpoints qui le renvoient.
Pourquoi ce formalisme
Le registre des types de problème de RFC 9457, en tableau.
Source
x-error-catalog et x-codes d'openapi.yaml : le catalogue ne peut pas diverger du contrat d'API.
