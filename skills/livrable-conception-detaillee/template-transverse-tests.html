Stratégie de test technique : ce que testent les devs

Les tests unitaires et d'intégration que les devs écrivent avec leur code. Les e2e des critères Gherkin relèvent du QA. Chaque test d'une règle cite son RG-xx (CF-56).

Version v0.1 Date JJ.MM.AAAA Auteur Architecte Statut brouillon

Outillage

À quoi sert
Dire avec quoi les devs testent.
Contenu
Les outils de chaque niveau (unitaire, intégration, composant) et leur environnement.
Pourquoi ce formalisme
L'outillage du socle de stack appliqué au produit, en liste de définitions : un niveau par terme.

runners back et front du socle, base de test, horloge fixe, ce qui est simulé

Cas imposés

À quoi sert
Dire ce que chaque test doit couvrir, pour qu'un ticket ne se rende pas sans.
Contenu
Une ligne par cible (objet du domaine, traitement, dépôt, route, composant), avec son niveau de test et ses cas.
Pourquoi ce formalisme
Un tableau cible, niveau, cas se relit comme une check-list en revue (CF-56, CF-57).
Lire
Les cas limites d'un traitement sont dans sa page : cités ici, jamais recopiés.

Points ouverts

À quoi sert
Lister ce qui reste à trancher sur les tests.
Contenu
Un point par ligne, rangé par impact décroissant : le sujet, l'hypothèse que le code suit en attendant, la question Q-xxx si elle est posée au PO.
Pourquoi ce formalisme
Un tableau, parce que chaque point a les mêmes attributs et se compare aux autres.
Lire
  • fort la réponse peut changer le modèle de données, une opération figée du contrat d'API ou ce qui structure tout le code
  • moyen la réponse peut changer une opération provisoire, un traitement, un schéma non figé ou un écran
  • faible la réponse ne change qu'un libellé, un message, une valeur ou un cas limite
Source
Écrit ici une seule fois ; le générateur le reprend dans la vue des points ouverts.
